Base Utilities Documentation

Base Utilities is a foundational package deployed to every client org. It provides error logging, automation kill switches, a trigger framework, and common screen flow resources.

1. Error Logging

Errors are captured as platform events and stored as Error_Log__c records. This provides transaction isolation: errors are logged even if the originating transaction rolls back.

From Apex (try/catch)

try {
    // business logic
} catch (Exception ex) {
    ErrorLogger.log(ex, 'MyClassName', 'myMethod');
}

From Apex (full parameters)

ErrorLogger.log(
    'ClassName',       // class or flow name
    'methodName',      // method or element
    'Error message',   // the error message
    'stack trace',     // stack trace or context
    recordId,          // related record ID (optional)
    'WARNING',         // severity: ERROR, WARNING, INFO, DEBUG
    'Integration'      // source: Apex, Flow, Integration, Other
);

From Flows

  1. Add a Fault Path from any element that can fail.
  2. On the fault path, add an Action element.
  3. Search for the action: "Log Error".
  4. Fill in the inputs:
InputRequiredValue
classNameYesYour Flow API name
methodNameNoThe element that failed
errorMessageYes{!$Flow.FaultMessage}
recordIdNo{!$Record.Id} if applicable
severityNoDefaults to ERROR
sourceNoDefaults to Flow

Verbosity Levels

The Error_Log_Settings__c.Verbosity_Level__c custom setting controls which messages are logged:

SettingLogs
DEBUGEverything (DEBUG, INFO, WARNING, ERROR)
INFOINFO, WARNING, ERROR
WARNINGWARNING, ERROR
ERRORERROR only

Email Notifications

Set Enable_Email_Notifications__c = true and provide Email_Recipients__c (comma-separated) in Error Log Settings to receive email alerts when ERROR severity logs are created.

Log Retention

A scheduled batch job (ErrorLogRetentionBatch) runs daily and deletes Error_Log__c records older than the configured Log_Retention_Days__c (default: 90 days).

2. Kill Switches

Hierarchy custom settings provide layered automation and validation rule control:

Custom SettingPurposeNaming Convention
Global_Kill_Switch__cDisable ALL automations + outbound emailsDisable_All__c, Disable_Outbound_Emails__c
Object_Kill_Switch__cDisable all automations for one objectDisable_[ObjectName]__c
Automation_Kill_Switch__cDisable a specific automationDisable_[AutomationName]__c
Validation_Kill_Switch__cDisable validation rules for one objectDisable_[ObjectName]__c

As hierarchy custom settings, these support org-default, profile-level, and user-level values.

Email Kill Switch

The Disable_Outbound_Emails__c field on Global_Kill_Switch__c suppresses outbound emails from automations without disabling the automations themselves. Use during data migrations or sandbox testing.

In Apex, check before sending: if (!KillSwitchHelper.isEmailDisabled()) { Messaging.sendEmail(...); }

In Flows, add a Decision element checking: {!$Setup.Global_Kill_Switch__c.Disable_Outbound_Emails__c} = FALSE

Validation Rule Kill Switch

The Validation_Kill_Switch__c setting lets you bypass validation rules per object without deactivating them. This is separate from Object_Kill_Switch__c so you can disable automations and validation rules independently.

Each validation rule must include a check in its formula:

AND(
    NOT($Setup.Validation_Kill_Switch__c.Disable_Account__c),
    /* actual validation logic */
)

Checking Automation Kill Switches in Flows

Add formula conditions to your flow's entry criteria:

{!$Setup.Global_Kill_Switch__c.Disable_All__c} = FALSE
AND {!$Setup.Object_Kill_Switch__c.Disable_Account__c} = FALSE
AND {!$Setup.Automation_Kill_Switch__c.Disable_My_Flow__c} = FALSE

Adding New Kill Switches

  1. Go to Setup > Custom Settings.
  2. Click Manage on the appropriate setting.
  3. Add a new Checkbox field: Disable_[YourName]__c, default unchecked.
  4. No code changes needed for automation/object kill switches. KillSwitchHelper uses dynamic field access.
  5. For validation rule kill switches, also update each validation rule formula to include the $Setup check.

3. Trigger Framework

The framework enforces one trigger per object and one handler per object. Kill switches and recursion prevention are built in.

Creating a New Trigger

// MyObjectTrigger.trigger
trigger MyObjectTrigger on MyObject__c (
    before insert, before update, before delete,
    after insert, after update, after delete, after undelete
) {
    new MyObjectTriggerHandler().run();
}

Creating a New Handler

public with sharing class MyObjectTriggerHandler extends TriggerHandler {
    public MyObjectTriggerHandler() {
        this.objectName = 'MyObject';
    }

    protected override void afterUpdate(
        List<SObject> newRecords,
        Map<Id, SObject> oldMap,
        Map<Id, SObject> newMap
    ) {
        // Check automation-level kill switch inline
        if (!KillSwitchHelper.isAutomationDisabled('MyObject_FeatureName')) {
            MyObjectService.doSomething(newRecords, oldMap);
        }
    }
}
Sharing: Always declare an explicit sharing keyword on handler classes. Use with sharing by default. The base TriggerHandler uses inherited sharing, so it takes on the subclass's sharing context.
Recursion: By default, each handler runs once per trigger operation per transaction. Set this.allowRecursion = true in the constructor only if re-entry is intentional.

7. Email Scrubber Tool

The Email Scrubber is a sandbox utility that appends .invalid to email address fields across any configured object, preventing sandbox orgs from sending emails to real end users.

Sandbox use only. This tool permanently modifies email field values for every record on the configured objects. Do not run it in production.

How It Works

The tool is driven by Email_Scrubber_Config__mdt custom metadata records. Each active record identifies one object and one email field to scrub. When the scrubber runs, it launches an Apex batch job (EmailScrubberBatch) that processes each configured object in sequence, appending .invalid to any non-blank email value that does not already end in .invalid. Records are processed in batches of 200.

Setup

  1. Assign the Email Scrubber Admin permission set to any admin who needs access. This permission set includes the Run_Email_Scrubber custom permission, which is required server-side to save configurations and run the scrubber. Users without this permission will see an access denied banner and the New Config, Edit, and Run buttons will be disabled.
  2. Open the Email Scrubbing tab in the Base Utilities app.
  3. Click New Config and create a configuration record for each object/field pair you want to scrub. Set Active to on.
  4. Click Run Email Scrubber to start the batch job.

Configuration Fields

FieldDescription
LabelHuman-readable name for the configuration (e.g., Contact – Email).
Developer NameAuto-generated unique identifier. Cannot be changed after creation.
Object API NameAPI name of the object whose email field should be scrubbed.
Email Field API NameAPI name of the email-type field on that object.
ActiveOnly active configurations are included when the scrubber runs.

Running the Scrubber

Click Run Email Scrubber on the Email Scrubbing tab. A status badge and progress counter appear while the job runs. You will receive a success or warning toast when the job completes. The tool polls for status every 3 seconds automatically — no need to refresh.

The job is idempotent: re-running it on a field that already ends in .invalid has no effect.

Production org protection. If the tool detects a production org, a warning banner is displayed at the top of the component. Clicking Run Email Scrubber will then show a confirmation dialog before the batch starts. The job will not run unless the user explicitly confirms. If the org type cannot be determined, the tool defaults to treating the org as production.
Kill switch. To halt the scrubber without removing the permission set, check Disable_Email_Scrubber__c in Setup > Custom Settings > Automation Kill Switch. The batch will refuse to start and return a user-facing error.
Partial failure handling. The batch uses Database.update(records, false) so a single failing record does not roll back the entire chunk. Failures are captured and logged as a single Error_Log__c entry per batch chunk, not per record.

Adding or Editing Configurations

Use the New Config button or the Edit button on any existing row. The object field is a searchable dropdown — type the object label to filter results. The email field dropdown automatically populates with email-type fields for the selected object once an object is chosen.

Configuration changes deploy via the Metadata API and take a few seconds to reflect. Click Refresh after saving a new config to see it in the table.

Deactivating a Configuration

Click Edit on the config row, toggle Active off, and save. Inactive configurations are visible in the table but are excluded from the next scrub run.

6. Post-Deployment Steps

  1. Schedule the retention batch: run scripts/setup/schedule-retention-job.apex in Developer Console.
  2. Set org-default values for Error_Log_Settings__c (especially User_Facing_Error_Message__c).
  3. Assign permission sets to appropriate users.
  4. Verify by running: ErrorLogger.log('TestClass', 'testMethod', 'Test error', '', '', 'ERROR', 'Apex');
